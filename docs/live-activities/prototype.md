# Transaction Live Activities

Live Activities start automatically for eligible broadcasts in all iOS build configurations, subject to the system Live Activities permission. No in-app enablement or amount setting is required. Transaction details follow the existing hidden-balances preference. Native macOS has no ActivityKit dependency.

This implementation uses **native-only, best-effort updates**, with no backend changes. On background entry, an existing eligible activity gets a UIKit background assertion for up to 25 seconds (less if iOS expires it), with an immediate observation followed by the foreground polling defaults: each native chain’s `ChainStatusConfig.pollInterval`, 10 seconds for market swap providers, and 60 seconds for limit orders. Per-record due times keep faster chains from accelerating slower ones, and limit orders retain elapsed time since the provider’s last sender poll. On each background entry, one BGAppRefresh request asks for a single pass after the earliest active record’s next polling interval, instead of waiting 15 minutes. Each delivered pass may request another while eligible work remains. iOS decides whether and when it runs; this is not a recurring timer or a guarantee of updates after suspension or force-quit. Disabling Background App Refresh or scheduler denial does not prevent the short UIKit continuation.

The card shows only **In progress**, **Success**, or **Failed**, without submitted/updated timestamps or delay labels. The richer tracker phases remain in the payload and transaction details. Confirmed sends, settled swaps and filled orders show Success; verified failures, refunds, cancellations and expired orders show Failed. Source-only settlement and tracking expiry remain In progress because their final outcome is unverified.

The app and widget compile the same `CircularProgressIndicator` source. The widget uses its static arc with a one-second rotation on content updates; the main app retains its continuous timeline. Reduce Motion, reduced luminance, stale content and terminal tracker phases suppress rotation. WidgetKit limits custom animations to two seconds; continuous spinning is not guaranteed.

Every nonterminal content state has a stale date 90 seconds after its last actual transaction observation. A healthy RPC lookup returning notFound supplies no newer transaction evidence, so the last positive observation timestamp remains unchanged. During the chain’s first polling interval after broadcast, a missing hash emits no delay; later misses mark the observation delayed internally. Foreground and native background observations use the same grace rule. Network errors, missing provider indexing and expiration never become transaction failure. Ordinary foreground tracking resumes when the app returns.

## Native background execution

The refresh path only observes recognized active records whose identity, vault, age, permission and durable status remain valid. It never creates or promotes an activity. Sends, approvals and generic transactions reuse the chain-status service. SwapKit reuses its provider tracker without advancing continuous-poller failure/give-up clocks. Native THORChain/Maya swaps query Midgard on their protocol network, including BTC/EVM inbound hashes. Limit orders reuse their authoritative order tracker, with at least 60 seconds between sender observations and the existing two-missing-polls protection. Known same-chain generic swaps settle atomically on successful native confirmation; other generic routes finish as **Source confirmed**, explicitly observing only the broadcast source. Source confirmation never claims cross-chain destination settlement. Identity and eligibility are checked again after network awaits, and cancellation discards late responses.

`TransactionActivityBackgroundRunner` owns exactly one window. Foreground entry, no remaining work, no further poll fitting in the observation window, the 25-second deadline or OS expiration ends it. At 22 seconds the runner stops network observations and reserves the remaining three seconds for queued ActivityKit writes; OS expiration still releases runtime immediately. Generation-scoped cleanup prevents an older task from ending a replacement. Scheduled refresh performs one pass, waits for serialized ActivityKit writes during normal completion and reports completion exactly once. If the immediate UIKit window is already running, scheduled delivery preserves that window instead of replacing it. Expiration cancels work and releases runtime immediately without waiting for network cleanup. Pending requests are cancelled when no eligible activity remains; status events do not continually postpone the next request. Interrupted terminal writes can be recovered from the persisted terminal binding on the next reconciliation. Normal native transaction polling resumes on foreground even if the activity was dismissed, and completed sends retain the wallet balance-refresh signal.

AppDelegate registers `com.vultisig.wallet.transaction-activity.refresh` before launch completes; the app plist declares that identifier and the `fetch` background mode. The app can receive a cold background launch without a scene, so the refresh core starts its own history-event subscription. SwiftData/keychain access can still be unavailable on a locked device; that fails closed and leaves honest stale content.

iOS 26 continued processing is intentionally not used: it presents system progress UI and expects measurable progress, which waiting for chain/provider settlement cannot reliably provide. This implementation supports the existing iOS 17 minimum. Apple's [background execution overview](https://developer.apple.com/videos/play/wwdc2025/227/) explains the system-controlled runtime and scheduling limits.

## Automatic coverage

- Every device that actually broadcasts records its accepted hash independently of Done. A successfully broadcast approval is recorded immediately even if the following transaction fails. Duplicate RPC responses resolve to the locally computed hash before recording. Signing-only payloads and unconfirmed failures do not create activities.
- All broadcast payloads are covered: ordinary and maximum sends, swaps, approvals, contract/staking operations, trust-line activation, limit placement/cancellation and accepted QBTC proof-service claim results. Generic non-transfer receipts do not invent transferred amounts. Their links open the existing transaction-history details sheet.
- THORChain/Maya market routes carry native protocol tracking metadata at the initial save. SwapKit routes carry SwapKit metadata; limit orders retain their existing tracker. Native market completion/refunds require matching authoritative inbound actions, and missing/unknown responses convey delay rather than failure.
- Known atomic same-chain generic swaps finish as completed after native confirmation. Generic cross-chain/unknown routes currently track the broadcast source only and end as Source confirmed; there is no destination-settlement claim for these routes.
- Maximum-send amounts remain absent until a richer receipt supplies the final amount. Quoted destination amounts are never labelled as received. The swap summary shows source amount and destination ticker, omitting an unknown destination. Fees remain estimates when available.
- There is no application-level two-card cap. Every fresh receipt is offered to ActivityKit; iOS enforces system capacity and permission. History tracking starts independently of ActivityKit admission. Rejected or dismissed activities are not promoted later.

## Lifecycle and privacy

The app persists an opaque-record binding and one-shot admission decision, keyed internally by a digest of vault + chain + hash. Dismissal, permission denial, request rejection, deletion and system capacity rejection cannot cause a restart. On foreground, it reconciles system activities against saved bindings and history. Fetch errors preserve stale content; missing/deleted records or vaults end it. A crash in the request/persistence window may end the orphan rather than risk restarting it. Tracking ends at the next reconciliation after 7.5 hours, with the system's own maximum lifetime as the suspended-app backstop.

The existing history store uses vault + hash identity. Cross-chain hash collisions fail closed for activity admission and do not create an ambiguously mutable extra row. Migrating that history identity is outside this increment. Earlier broadcast rows accept missing amount/fee/fiat enrichment from Done while preserving the original ID, status, tracker and existing nonempty receipt values.

Admission decisions survive upgrades and suppress repeated requests within the activity lifetime. Ended decisions older than the 7.5-hour maximum lifetime are pruned once the system no longer retains their activity; records past that lifetime cannot be admitted. Active or system-retained receipts keep their bindings for terminal-write recovery and privacy cleanup. A history reset followed by a newly recorded broadcast after the retention window is treated as a new admission decision.

All ActivityKit writes are serialized. Stale observations cannot overtake newer timestamps; terminal outcomes cannot regress. Privacy changes redact mutable payload data, including retained terminal cards. Hidden balances redact details both at admission and on subsequent privacy changes. Static attributes contain only the random local record UUID. Full recipient addresses are shortened inside the shared state initializer. Vault names, public keys, hashes, addresses in full, memos and signing material never enter the widget payload.

The link uses `vultisig://transaction/<local-record-uuid>`. ContentView queues it behind splash/passcode, drops it behind key-share recovery, then resolves both the record and its vault locally and opens the normal transaction-history details sheet. It does not depend on whichever vault is currently selected. Deleted records or vaults show the localized unavailable message through the existing app error presenter. Opening a valid record uses the history screen’s existing polling/tracking and receipt refresh. Dismissing the sheet returns to that vault’s transaction history.

## Contract and validation

`TransactionActivityState` is a Codable value shared by the app and widget. It uses `VultisigUIResources` for generated image-catalog membership and has no ActivityKit dependency itself. Its date encoding uses Swift JSONEncoder's default seconds-since-2001 strategy. There is no APNs contract in this native-only increment. Combined attributes + state are validated below 4096 bytes at request; every optional string has a scalar-wise UTF-8 bound, including pathological combining characters.

Unit tests cover privacy, byte budget, links, status/freshness semantics, lifecycle restoration/dismissal/limits/permission/deletion, full/partial provider refunds, receipt enrichment and durable storage notifications. Lifecycle tests inject a fake ActivityKit client, local lookup, no-op polling hook, prepared-cache lookup and controlled image loader. Image regressions cover catalog identifiers, old payloads and malformed keys, hidden balances, nonblocking admission/status updates, fresh-row completion without invented freshness, retention renewal, URL replacement and late cancellation without resurrection. The implementation agent runs generation/lint and local read-only cross-model review. The parent owns the full iOS test gate, macOS build and runtime acceptance; those must pass before any shipping claim.

## Branded card iteration

The card uses the canonical 401-image catalog in `VultisigUIResources` when the durable receipt contains an exact local logo ID, including RUNE and chain badges. Source and destination images use `coinLogo` and `toCoinLogo` for both swaps and limit orders; a ticker never selects an image. Rendering tries validated bundled art, a prepared shared-cache PNG, then the existing neutral asset glyph. The widget only performs bounded synchronous file reads and never starts image tasks or network requests.

After a successful activity request, the app prepares HTTPS images asynchronously through the shared image loader and App Group `group.com.vultisig.wallet`. Preparation never blocks admission or transaction status writes. Admission can immediately use images prewarmed by normal app views; preparation also renews cached-image protection for the activity lifetime. One job per accepted record identity and URL signature avoids repeated downloads during reconciliation and status updates. Restored active bindings may prepare images without admitting new activities.

Optional `sourceImageKey` and `destinationImageKey` contain only validated 64-character lowercase hexadecimal cache keys. Missing keys default to nil in old schema-v1 payloads; bundled identifiers remain optional as well. Hidden balances omit all bundled and cached-image identifiers and cancel preparation. Deletion, dismissal, expiry, terminal status, permission loss and identity or source-image changes also cancel obsolete jobs. After an await, image completion revalidates the current record, active binding, authorization and privacy, then enters the existing serialized update queue with a fresh row and `observedAt: nil`. It preserves the delayed flag and cannot make transaction evidence look newer or resurrect an activity. No image bytes or raw URLs enter ActivityKit.

The loading symbol makes one short pulse on fresh transaction observations, with no looping animation or invented progress. Reduce Motion, Always On luminance reduction, stale observations and terminal outcomes suppress processing motion. Status color distinguishes success, failure, refund and tracking end. The rich card falls back to its core header/hero/freshness layout within the 160-point Lock Screen budget.

Widget previews cover transfer, swap, private, delayed and failure states with bundled token art. The Lock Screen card fits within 160 points including padding; optional detail rows yield to status, amount and freshness. Real locked-device timing and automatic BGAppRefresh delivery require signed-device validation.

## Testing automatic admission

Build and run this branch on iOS (Debug or Release). No preview toggle is needed. With system Live Activities allowed, a successful broadcast starts an activity after a usable hash and saved receipt while the app is foreground. Test a native THORChain swap (including a BTC/EVM source), Maya, SwapKit, an ordinary send, maximum send, approval, contract/staking operation and limit placement/cancellation. An already missed or dismissed transaction is not restarted. Multiple broadcasts are offered to system capacity. Hide balances to redact amounts and asset identity. Ordinary push-notification settings are separate.

Use the widget previews for rendering checks. Coordinator regression tests verify automatic admission with fresh defaults, OS permission changes and hidden balances. The app has no synthetic activity launch mode.

## Testing native updates

Runner tests cover injected scheduled delivery, scheduler denial, expiration, foreground handoff, replacement races and exactly-once completion. Simulator may reject BGTaskScheduler submission, so do not interpret a manually invoked handler as proof of automatic scheduling.

On a signed device, make an eligible test transaction through the normal send/swap flow and immediately lock or background the app. Confirm the existing activity observes chain confirmation or provider settlement during the granted window. Also test slow settlement beyond that window, Background App Refresh disabled, offline recovery, app return, activity dismissal, vault/history deletion, multiple concurrent activities and force-quit. After the short window, delayed content is expected until iOS grants refresh or the app returns. No fixed update latency is promised.
